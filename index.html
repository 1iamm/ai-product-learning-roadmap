PRODUCT DESIGN / 4-WEEK STUDY PLAN

发现重要需求，
做出有价值的产品。

为有工程背景、正在参与 SaaS 产品设计的你，建立从需求取舍、交互方案到效果验证的完整判断。

HOW WE LEARN

一周一个判断，
留下可以讨论的依据。

周次表示建议顺序，可以跨周完成。阅读、草稿和自检分别记录；读完材料不等于掌握。

  1. 读指定部分带着本周问题找依据，不追求把整站读完。
  2. 先写自己的判断区分原文事实、作者解释与个人假设。未知就写未知。
  3. 带回对话，再修订复制讨论提纲，请助手评审依据与取舍，逐个追问。
贯穿四周的 B2B 案例：怎样判断一个新产品值得做？＋

使用 Product Talk 的 Evaluating If a New API is Needed（2025）↗。案例团队调查了人工处理订单的困难，探索 API 产品；上线后，又面对部分大客户没有优先采用的问题。

第 1 周比较需求与证据；第 2 周为其中一个任务构思可视化后台；第 3 周制定验证方法；第 4 周评估整个产品。第 2 周的界面是教学延伸，原文没有这个 UI；文章中的效果属于案例受访者陈述。

也可以换成你熟悉的 SaaS，但不必提供内部业务资料。没有真实用户或数据时，先交付验证方案，保留待验证项。

本周交付

带着它回来讨论

一页需求判断卡

  1. 从公开案例找出 2–3 个候选问题。每个问题写清谁受影响、什么情境、现在怎么办，以及文章提供了什么依据。
  2. 比较影响范围、发生频率、严重程度、现有替代办法和业务目标关联；资料没有提供的信息写“未知”。
  3. 选一个优先问题，解释取舍。提出 3 个能补足证据的访谈问题，并写出什么新证据会让你改选。
判断时多想一步

问题的重要性和某个方案的开发成本分开考虑。先选值得探索的问题，再比较可行办法；不要把大客户提出的功能自动当成最高优先级。

NN/g · 2016.12.04 · 基础方法

Wireflows ↗

阅读范围 读 Wireflows as a Deliverable 与 Wireflows Document Interactions

看页面草图如何与操作连接，尤其是一次点击后信息或反馈怎样变化。无需学习绘图工具。

本周交付

带着它回来讨论

两套草图 + 一条任务流程 + 选择理由

  1. 承接 Week 1 的问题，确定一个具体任务及成功结果。使用原文案例时，可假设为“创建并提交一笔服务订单”设计可视化后台。
  2. 列出用户每一步要知道什么、做什么决定、得到什么反馈。用纸笔、文字或任意工具画两套不同方案。
  3. 把选定方案的页面草图与操作连起来，说明入口、信息顺序、默认值、主要动作的理由；列出最需要验证的设计假设。
判断时多想一步

可视化后台是教学延伸，原文没有给出这个界面。方案可以改变任务的做法；不必照搬现有步骤，也不以步骤越少作为唯一标准。

WEEK 3 / 需求验证

证明一个需求被做好了

写本周作业 ↘

除了开发完成，怎样知道用户用得好、问题也改善了？

分开验证功能正确性、可用性与实际效果，并提前写清评价标准。

Usability Testing 101 ↗

阅读范围 重点读 Elements 与 Types of Usability Testing

02
Product Talk · 2026.03.18 · 正文可读

Outcomes vs. Outputs ↗

阅读范围 读公开正文，跳过文末 Outcome Coach

关注交付物、客户行为变化、业务结果的区别，以及为什么单个功能的使用量可能误导。文末付费工具不是学习要求。

本周交付

带着它回来讨论

一张需求验证卡 + 一份任务测试记录

  1. 为 Week 2 的方案写 2 个中性的任务情境，明确找什么样的人测试，观察成功、犹豫、错误和求助。任务描述不要泄露按钮或答案。
  2. 为原始问题定义结果指标：统计对象、分母、基线、期望变化、观察周期和不能恶化的指标。缺少数据时写待采集，不填“估计的实际值”。
  3. 有合适参与者时做一次探索性测试；没有时，先完成脚本和认知走查，结果栏标“未开展真实测试”。据证据决定下一步。
判断时多想一步

自测、助手评审和假设推演可以找问题，但不能替代真实用户证据。上线前后的变化也可能受其他因素影响，需记录对照方式与局限。

Product Talk · 2026.03.18 · 正文可读

Outcomes vs. Outputs ↗

阅读范围 回读 business / product outcomes 与 traction metrics 的讨论

把客户结果、行为信号、业务结果分开；学习怎样让产品指标支持决策。

本周交付

带着它回来讨论

一页产品判断备忘录

  1. 沿用公开案例或选自己的 SaaS，写清核心客户、最重要的问题、替代办法，以及产品为什么值得被选择。
  2. 列出价值获得、采用与持续使用、商业持续性三方面的证据和缺口。建立一条“客户收益 → 行为信号 → 业务结果”的假设链。
  3. 汇总前三周判断，给出继续投入、先验证或调整方向的建议；列出两项下一步行动，以及什么证据会改变当前结论。
判断时多想一步

按产品的自然使用周期判断。续费需要结合真实使用和留下的原因；获客、实施、支持成本也要考虑。没有财务或客户数据时，交付评估方法和待验证假设。
